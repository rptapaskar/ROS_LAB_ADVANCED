“another syllabus topic.”

Core idea: ROS 2 lets separate software components communicate. In robotics, that communication becomes powerful because the components can be connected to real sensors, controllers and actuators.
01 · THE ROS 2 MENTAL MODEL

Think of ROS 2 as
a digital nervous system.

A robot is made of many jobs. ROS 2 gives those jobs a structured way to discover each other and exchange information.

NODEA program/component doing a job.
PUBLISHERA node that sends data.
TOPICA named communication channel.
MESSAGEThe typed data travelling through it.
SUBSCRIBERA node receiving the data.
THE COMMUNICATION CHAIN
Publisher
“I have data!”
→
Topic
/sensor_data
→
Subscriber
“I need data!”

The publisher and subscriber do not need to call each other directly. They communicate through a named topic using a defined message type.

02 · BUILD YOUR FIRST ROS 2 WORKSPACE

Workspace → package → node
→ launch.

The exact package name, Python executable structure and robot-specific paths depend on the laboratory setup. The workflow below explains the concepts and standard command patterns.

student@robot:~
$ mkdir -p ~/ros2_ws/src
$ cd ~/ros2_ws
$ colcon build
Starting >>> ...
Finished <<< ...
Summary: ...
$ source install/setup.bash
$ cd src
$ ros2 pkg create --build-type ament_python my_first_pkg
$ cd ~/ros2_ws
$ colcon build --symlink-install
$ source install/setup.bash
WHY EACH STEP EXISTS

1. Make the workspace

~/ros2_ws is a convenient workspace directory. The src directory is where your source packages live.

2. Build with colcon

colcon build processes packages in the workspace and creates build/install/log areas.

3. Source the overlay

source install/setup.bash updates the current shell environment so your built workspace becomes discoverable.

4. Create a package

ros2 pkg create generates the package skeleton. The ament_python build type is appropriate for a Python ROS 2 package.

5. Rebuild + source

After adding/changing code, rebuild as required and source the resulting environment in the shell where you want to run the package.

Overlay concept: ROS 2 can combine an existing underlay with your own workspace overlay. If your shell has not sourced the right setup file, ROS 2 may not discover packages you just built.

04 · MESSAGE TYPES

A topic has a name.
But a message has a shape.

The experiment specifically asks you to review the message definitions used by the robot's command, odometry and sensor streams.

geometry_msgs/Twist

Velocity command

Represents velocity components. In this lab it is associated with /cmd_vel, which is used to command robot motion.

nav_msgs/Odometry

Estimated motion

Contains odometry information including pose and twist, associated with the robot's estimated movement.

sensor_msgs/LaserScan

LiDAR scan

Represents planar laser range measurements with angular/range information.

sensor_msgs/Imu

Inertial data

Contains inertial measurements such as orientation-related information and angular/linear acceleration fields as provided by the sensor driver.

Debugging trick: When a topic “exists” but you don't understand it, use ros2 topic type /topic, then ros2 interface show TYPE, then ros2 topic echo /topic.

06 · RVIZ2 — SEE THE ROBOT'S DIGITAL WORLD

Numbers are useful.
Seeing them is powerful.

RViz2 turns streams of robot data into visual representations. The experiment asks you to visualise LiDAR, IMU, odometry and RGB-D data and identify the coordinate frame of each.

👁️

What to look for in RViz2

Do not just open RViz and say “it works.” Identify what each display represents, what topic supplies it, and which coordinate frame it is attached to.

Ask yourself:
What am I seeing? Which topic provides it? Which frame is it expressed in? Does the visualisation make physical sense?
📡 LiDAR

Observe the planar scan and relate the geometry in RViz2 to the physical surroundings.

🧭 IMU

Explore inertial information and understand that its interpretation depends on coordinate frames and sensor conventions.

🛞 Odometry

Observe the estimated robot pose/trajectory and relate it to the robot's movement.

👁 RGB-D

Explore depth information and understand that it represents a 3D sensing modality rather than a planar laser scan.

07 · TF2 + COORDINATE FRAMES

Robotics has a
coordinate-frame problem.

The experiment asks you to identify the coordinate frame of each visualised sensor. TF2 provides the framework for describing relationships between frames.

📍

Why frames exist

A LiDAR measurement is naturally associated with the LiDAR's physical frame. Robot motion and world/map representations may use other frames. To combine measurements correctly, their spatial relationships must be known.

🔗

What TF2 provides

TF2 maintains and communicates transformations between coordinate frames so software can transform information from one frame into another.

MENTAL MODEL
Sensor frame
“where I measure”
→
TF relationship
“how frames relate”
→
Robot/world frame
“where I interpret it”
Don't memorise frame names blindly. Your task is to understand why a measurement has a frame and why a visualiser needs that information to place the data correctly.
08 · DDS + DISCOVERY

How did that node
find that node?

The pre-lab activity asks you to study DDS-based discovery. At a conceptual level, ROS 2 uses DDS middleware to support discovery and communication between distributed ROS 2 entities.

📣

Discovery

ROS 2 systems can discover relevant participants and communication endpoints rather than requiring every node to be manually wired to every other node.

🌐

Distributed robotics

Nodes can be separated across processes and, depending on the configured environment/network, across machines. This is one reason ROS 2 is useful for complex robotic systems.

When things go wrong 😵

A node may exist but the expected data may not appear because the relevant communication path/configuration is not what you expected.

Engineer response 😎

Inspect the graph systematically: nodes → topics → types → publishers/subscribers → message flow → frames → application behaviour.

09 · ROS 2 BAG — RECORD REALITY

What if you could
replay the robot?

The session closes with recording a reference bag file. A bag captures selected ROS 2 data streams so they can be analysed later without requiring the physical robot to repeat the exact motion immediately.

ros2 bag
$ ros2 bag record /odom /scan /imu
[INFO] Listening for topics...
[INFO] Recording...
[INFO] Press Ctrl-C to stop.
$ ros2 bag info BAG_DIRECTORY
Files: ...
Duration: ...
Topics: ...
$ ros2 bag play BAG_DIRECTORY
[INFO] Playback started...
WHY THIS MATTERS

Record once. Analyse many times.

A bag can preserve a reference run for later inspection. That becomes valuable in subsequent experiments involving sensor analysis, odometry, fusion and navigation.

Think like a researcher: a recorded dataset is evidence. Preserve the conditions and document what was recorded so someone else can understand what the data represents.
Command caution: The exact topic set for the laboratory's reference bag should follow your instructor's procedure. Recording “everything” is not automatically better; record the streams required for the intended analysis.
10 · TROUBLESHOOTING MODE

When ROS says
“nothing is happening.”

Do not randomly restart everything. Diagnose from the graph outward.

🔴 Symptom: no node

Check whether the expected process is running.

ros2 node list

Then inspect how the system was launched.

🟠 Symptom: topic missing

Check visible topics and verify that the relevant driver/node is running.

ros2 topic list

🟡 Symptom: topic exists, no data

Inspect type and topic information, then observe it.

ros2 topic info /topic

ros2 topic echo /topic

🟢 Symptom: data exists, RViz wrong

Check the display configuration and coordinate frame relationships.

Think TF2 + frame + topic + display.

🔵 Symptom: package not found

Check whether the workspace was built and sourced in the current shell.

colcon build

source install/setup.bash

🟣 Symptom: behaviour surprises you

Stop physical motion safely first. Then inspect nodes, topics and commands. Safety comes before debugging.
