PACKAGE ANATOMY

One package, multiple jobs.

A typical Python package has a Python module directory, package metadata and an entry-point configuration. Each monitor becomes an executable entry point, while a launch file can bring up the complete monitoring system.

Why entry points? They let you expose Python functions as ROS 2 executables so you can run them using ros2 run.

The build loop

Edit → build → source → run → inspect → repeat. With --symlink-install, Python development is more convenient because installed files can point back to the source tree.

02 · THREE STREAMS · THREE STORIES

Don't just print messages.
Extract meaning.

The learning outcome explicitly asks you to interpret raw sensor messages, including invalid and out-of-range returns. Your monitor nodes should therefore calculate useful quantities rather than dumping entire messages.

📡
sensor_msgs/LaserScan

LiDAR monitor

Useful fields include angle_min, angle_increment and the ranges array. A sample's bearing can be related to its array index.

🧭
sensor_msgs/Imu

IMU monitor

Inspect inertial quantities and distinguish a stationary sensor's baseline/rest behaviour from motion-induced changes.

🛞
nav_msgs/Odometry

Odometry monitor

Observe pose and twist information and relate the reported values to the robot's stationary and moving states.

🧪
Health monitor

Turn raw data into evidence

Record publication rate, minimum range, bearing, invalid-return fraction and IMU rest bias in your observation sheet.

LaserScan mini-formula: for a valid range sample at array index i, the corresponding beam angle is commonly related to angle = angle_min + i × angle_increment. Your task is to understand the message structure and handle invalid/out-of-range values according to the sensor specification and lab procedure.
03 · CALLBACK DESIGN

Every message is
a callback event.

A subscriber callback runs when a message is delivered to the node. Keep the callback focused: receive → validate → extract → update/print the required observation.

SUBSCRIBEDeclare topic + message type.
RECEIVEROS 2 delivers a message.
VALIDATECheck ranges / validity.
EXTRACTCompute useful quantities.
REPORTLog, measure or store evidence.
monitor pattern
def callback(self, msg):
    # 1. validate
    # 2. extract
    # 3. interpret
    # 4. report

self.create_subscription(
    LaserScan,
    topic_name,
    self.callback,
    qos_profile
)

What belongs inside?

Validate: identify invalid/out-of-range samples before using them.

Extract: compute minimum valid range, associated bearing, invalid-return fraction or other required observation.

Interpret: connect the number to the physical experiment.

Report: log a concise result rather than flooding the terminal with giant message dumps.

Engineering rule: a monitor should make the data easier to understand, not merely make the terminal noisier.
04 · QUALITY OF SERVICE

QoS is the
communication contract.

The experiment deliberately uses quality-of-service mismatch as a fault. A subscriber can know a topic exists and still fail to receive data if the offered and requested QoS settings are incompatible.

🤝

Publisher offers

The publisher's QoS profile describes how it offers the data stream.

🙋

Subscriber requests

The subscriber declares what communication behaviour it can accept. Compatibility matters.

💥

Mismatch = no expected flow

The graph may still look alive while the expected subscriber callback does not receive the stream you thought it would.

🔬

Diagnose with evidence

Inspect topic information, endpoint details and your node's configuration rather than immediately rewriting code.

Experiment target: don't merely know the word QoS. Be able to explain how a QoS mismatch can create a communication failure and how you would prove that this is the cause.

06 · FAULT INJECTION ARENA

Now we deliberately
break the graph.

The second session is not additional coding time. It is diagnosis time. Your instructor can induce faults and you must use evidence to identify the failure and explain why the chosen fix resolves it.

💥 Fault A — QoS mismatch

Symptom: topic is visible, but your callback does not receive expected data.

Investigation → compare endpoint/QoS configuration → restore a compatible profile.

🔀 Fault B — Topic remap

Symptom: your node is listening, but the intended sensor stream is not arriving.

Investigation → inspect actual topic names and node connections → correct the remap/configuration.

🌐 Fault C — Domain conflict

Symptom: expected nodes/topics disappear from your graph even though another system may be running.

Investigation → compare ROS domain configuration → restore the intended domain setup.

🛑 Fault D — Driver termination

Symptom: a sensor stream stops because its producing driver/process is no longer running.

Investigation → inspect node/process state and topic endpoints → restore the approved driver bring-up.

07 · MEASUREMENT MODE

Stationary vs moving:
make the comparison.

The experiment specifically calls for measurement of sensor health while the robot is stationary and in motion.

🧍

Stationary baseline

Measure the sensor behaviour when the robot is not moving. This provides a reference for rest bias, background readings and invalid/out-of-range behaviour.

🏃

Motion response

Repeat the observation during controlled teleoperation and compare the sensor output with the physical event that caused the change.

📊

Record numbers

Publication rate, minimum range, bearing, invalid-return fraction and IMU rest bias belong in the observation record.

🧠

Interpret, don't worship numbers

A measurement is useful only when you can explain what physical quantity it represents, what frame it belongs to and what conditions produced it.
