01 · LIDAR GEOMETRY

Raw ranges are useless
until you know where they point.

A planar LaserScan contains an array of range measurements. Each array index corresponds to an angle determined by the scan geometry. Your first engineering job is to map the array correctly before making navigation decisions.

FRONT FIELD OF VIEW · SECTORISED

🧭 Sector extraction

Instead of processing every beam as a separate navigation decision, divide the scan into meaningful directional sectors such as front, left and right according to your lab design.

  • Read angle_min and angle_increment.
  • Map desired angular bounds to array indices.
  • Reject invalid measurements.
  • Compute a robust sector distance from the valid samples.
  • Feed the result to the controller.
Index mapping: for index i, the corresponding beam angle is commonly related to angle_min + i × angle_increment. Always respect the actual message convention and sensor configuration.
📐

Beam angle

θi = angle_min + i · angle_increment

Connect array position to physical direction.

📏

Free-space distance

dsector = robust statistic(valid ranges)

The exact statistic should follow your controller design; do not blindly use an invalid sample.

02 · DATA CLEANING

Before the robot reacts,
clean the signal.

Obstacle avoidance is safety-relevant. A single invalid or out-of-range value should not accidentally become a “wall detected!” command — and a real nearby obstacle should not be hidden by careless filtering.

READReceive LaserScan.
MAPConvert sector angles to indices.
FILTERHandle invalid/out-of-range values.
SUMMARISECompute sector distances.
DECIDEChoose motion behaviour.
sector logic
for i, r in enumerate(msg.ranges):
    angle = msg.angle_min
          + i * msg.angle_increment

    if not valid(r):
        continue

    if angle_in_sector(angle):
        sector.append(r)

distance = summarize(sector)

What does “valid” mean?

Your implementation should explicitly account for the sensor's validity conventions, including non-finite values and measurements outside the meaningful range described by the LaserScan message.

Why reject outliers?

Reactive control can be extremely sensitive to a single bad measurement. A robust sector estimate reduces accidental decisions while retaining awareness of genuine obstacles.

Rule: filtering is part of the controller design. Record what you rejected and why — especially during debugging.

04 · PARAMETERS

Hard-coded controller?
Nope.

The learning outcome requires thresholds and gains to be exposed as ROS 2 parameters and tuned experimentally. Parameters turn controller behaviour into something you can measure, compare and reproduce.

stop_distance

Distance below which the emergency-stop condition is triggered.

slowdown_distance

Distance at which the controller begins reducing forward speed before the stop threshold.

max_linear_velocity

Upper bound on commanded forward velocity for the experiment.

max_angular_velocity

Upper bound on commanded turning rate.

steering_gain

Gain relating wall/obstacle distance error to steering correction.

parameter_file

Configuration file holding initial values so experiments can be reproduced.

ROS 2 parameter workflow
$ ros2 param list /your_controller

$ ros2 param get /your_controller stop_distance

$ ros2 param set /your_controller stop_distance VALUE

$ ros2 param dump /your_controller

# Use your actual node name and approved
# parameter values/configuration.

Why parameters?

Suppose the robot brakes too late. You should be able to test the effect of changing stop_distance without editing the controller source.

Suppose wall following oscillates. You should be able to adjust the steering gain and evaluate the resulting behaviour experimentally.

Scientific habit: change one parameter deliberately, repeat the trial, record the outcome. Don't randomly turn ten knobs at once.

08 · FAILURE MODES

“It oscillates” is not
a diagnosis.

The experiment explicitly asks you to measure stopping distance, traverse time and failure modes, and explain oscillation and livelock. Treat behaviour as evidence about the controller.

🌀 Oscillation

The robot repeatedly steers left/right instead of settling into a stable path.

Possible clues: excessive gain, noisy/unstable sector estimate, poor geometry or insufficient damping/logic.

🔁 Livelock

The robot keeps reacting and moving but fails to make meaningful progress toward a safe traversable state.

Possible clues: repeated turn decisions, ambiguous free-space selection or controller logic that lacks progress/hysteresis.

💥 Late braking

The robot reaches an obstacle before stopping at the desired distance.

Possible clues: sensor latency, control period, mechanical braking distance, speed or threshold.

🧱 Wall crash

The robot cannot maintain safe clearance while moving alongside a wall.

Possible clues: sector selection, index mapping, steering gain, frame/geometry assumptions or speed.

🚪 Dead-end trap

The robot enters a dead end and cannot choose a productive escape behaviour.

This exposes the limits of purely local reactive decisions and motivates planning.

🚶 Moving obstacle

A moving object changes the local environment faster than the controller can safely react.

Compare sensing/control timing with obstacle motion; document the observed failure rather than hiding it.

10 · STOPPING DISTANCE

The robot doesn't stop
the instant you say “stop.”

The post-lab explicitly asks you to decompose measured stopping distance into sensor latency, control period and mechanical braking distance. This is one of the most important engineering insights in the experiment.

📡

Sensor latency

motion continues while sensing

The environment changes before the controller can react to newly sensed information.

⏱️

Control period

sample → compute → command

The controller operates discretely; a decision is not continuous in time.

🛞

Mechanical braking

robot still moves after command

Real actuators and wheels need finite time/distance to reduce motion.

📏

Total observed stop distance

≈ sensing + control + mechanical effects

Use measured data and your laboratory's defined decomposition when reporting the result.

Safety insight: a threshold alone does not guarantee a safe stop. Speed, sensing delay, controller period and physical braking all matter.
11 · REACTIVE NAVIGATION'S LIMIT

Sometimes the robot needs
a brain, not just reflexes.

A reactive controller responds to what it senses locally. That makes it simple and fast, but local decisions can fail in environments where the robot must remember where it has been or reason about a longer route.

⚡

Why reactive control is great

Simple, fast, local and easy to implement. Excellent for immediate obstacle avoidance and controller experiments.

🧩

Why it can fail

Dead ends, loops, ambiguous free space and moving environments can expose the limitations of purely local rules.

🐞

Bug-type connection

Simple Bug-style strategies use obstacle-boundary following plus goal-directed behaviour, but have known limitations. This experiment builds intuition for why planning matters.

🗺️

What comes next

Once sensing and reactive control are understood, higher-level planning can decide where to go rather than only how to react to the nearest obstacle.
