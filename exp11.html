00 · THE CAPSTONE

This is not
“just another lab”.

The uploaded brief defines Experiment 11 as an open-ended end-semester assessment. Teams of three select an application-oriented mobile robotics problem and are assessed on whether they can turn the problem into a measurable, validated autonomous system.

💡

Choose a problem

Examples in the brief include indoor waypoint delivery, human-aware navigation, dynamic-obstacle navigation, precision docking and a miniature factory/warehouse transport task.

🗺️

Build the world model

Generate an occupancy grid of the real environment using SLAM, then evaluate its dimensional and accuracy properties against a measured reference.

🧠

Build the autonomy stack

Bring up and tune Nav2, integrate perception, estimation, planning and control, and adapt the stack to your chosen application.

📊

Prove the claim

Define a baseline before implementation, benchmark the developed application against it over repeated runs, and defend the results technically.

The capstone mindset: you are not being assessed only on whether the robot moves. You are being assessed on whether you can make a falsifiable engineering claim, build a system to test it, measure the outcome and defend the evidence.

02 · SLAM

First, teach the robot
what its world looks like.

SLAM — Simultaneous Localisation and Mapping — is the first major stage in the capstone. The deliverable is not simply a pretty map. You must save the laboratory map and assess its dimensional accuracy against tape-measured references.

SLAM CONCEPT
RANGE SCANS

SCAN MATCHING

LOOP CLOSURE

MAP UPDATE

SAVED MAP
navigation world model
📡

Scan matching

Successive observations are compared to infer motion and align the robot with the evolving map.

🔁

Loop closure

Returning to a previously observed area provides information that can reduce accumulated mapping error.

🧩

Particle-filter localisation

The brief asks students to study particle-filter localisation as part of the conceptual basis of the mapping/navigation pipeline.

📏

Map accuracy

Compare selected map dimensions with tape-measured references. Report the discrepancy rather than assuming the map is correct.

Important distinction: a visually convincing occupancy grid is not automatically dimensionally accurate. Your assessment requires measured evidence.

Now turn the map

🗺️

Costmaps

Convert environmental and sensor information into a representation used to reason about traversable and occupied space.

🛣️

Planner

Produces a path or route toward the navigation objective within the configured navigation representation.

🎮

Controller

Turns the planned path and current state into motion commands that the robot can execute.

🧭

Localisation

Maintains the robot's estimated pose relative to the navigation world model so planning and control have a meaningful state.

Nav2 tuning is not “find the magic YAML”. The project asks you to tune the stack for the application and defend every tuned parameter against your team's own measurements from Experiments 4–10.
05 · TUNING

Parameters are
engineering decisions.

The technical report must defend every tuned parameter against measurements from the preceding experiments. The exact parameter names and values depend on the approved Nav2 configuration used in the laboratory; the table below is a reasoning framework, not a replacement for that configuration.

🧱 Costmap inflation

Controls how obstacle proximity is represented around occupied regions and therefore affects clearance and path choices.

JUSTIFY → measured obstacle / clearance behaviour

🏎️ Speed limits

Influence travel time, stopping behaviour and controller aggressiveness.

JUSTIFY → Experiments 04–05 + safety evidence

🌀 Controller gains

Influence how aggressively the robot responds to path or heading error.

JUSTIFY → measured trajectory response

🗺️ Planner settings

Shape how paths are generated for the environment and application.

JUSTIFY → path quality / success evidence

📡 Sensor configuration

Determines what perception information is available to navigation and under which conditions.

JUSTIFY → Exp 08 comparative sensor evidence

🧭 Localisation configuration

Affects the quality of the pose supplied to planning and control.

JUSTIFY → Exp 07–09 localisation evidence

🔄 Recovery behaviour

Defines what the stack should attempt when normal navigation cannot progress.

JUSTIFY → Exp 10 state/recovery analysis

🛡️ Safety limits

Keep application behaviour within the independently defined safety envelope.

JUSTIFY → Exp 05 + Exp 10 evidence

🎯 Goal tolerances

Define what “arrived” means for the selected application.

JUSTIFY → application requirement + baseline

08 · BASELINE + BENCHMARK

Measure first.
Then claim improvement.

The brief explicitly requires a baseline to be defined before implementation. The developed application is then benchmarked against that baseline over repeated runs, with dispersion reported.

Bad claim: “Our robot is better.”
Engineering claim: “Under the defined scenario and repeated-trial protocol, our application changed metric X from the measured baseline by Y, with dispersion Z, while maintaining the stated safety condition.”

12 · COMMON TRAPS

Don't let a cool
demo hide weak science.

🎨

“The map looks good.”

Visual quality is not the same as dimensional accuracy. Measure it.

⚙️

“We tuned until it worked.”

That is not a defensible tuning process. Record the parameter, evidence, change and effect.

🏆

“One successful run.”

The brief asks for benchmarking over repeated runs and dispersion. Reliability matters.

🧩

“Every component works separately.”

The learning outcome is integration: perception, estimation, planning and control must operate as one autonomous application.

📈

“Our number improved.”

Improved relative to what? Without a measured baseline, improvement is an unsupported claim.

🤖

“Nav2 did it.”

Your project is not just Nav2 bring-up. The application-specific design, tuning, integration and validation are yours.
