01 · FIRST, KNOW WHAT YOU'RE GETTING INTO

So… what is this lab?

It is not a “follow the manual and get the output” lab. The course is deliberately designed to move you from guided learning → implementation → investigation → open-ended engineering.

🤖

A real mobile robot

You work with a differential-drive platform and its drive train, wheel encoders, IMU, RPLIDAR, RealSense depth camera, controller, computing unit, battery and emergency stop.

🧠

A real robotics software stack

You learn Linux, ROS 2 workspaces and packages, nodes, topics, messages, launch files, RViz2, data recording, transforms and the tools used to make robot software run.

📡

Robotics is a sensing problem

You will work with LiDAR, IMU, odometry and RGB-D data — including invalid readings, sensor limitations, bias, drift and fault conditions.

🧪

Engineering, not just coding

You will measure, repeat trials, analyse data, diagnose faults, justify parameters and defend conclusions from evidence.

COMMANDSoftware tells the robot what to do.
COMPUTEROS 2 moves information between nodes.
ACTUATEController → motors → wheels.
SENSEEncoders, IMU, LiDAR, RGB-D.
DECIDEEstimate → plan → control → repeat.
02 · YOUR 48-HOUR JOURNEY

You don't start as an expert.
You become one.

The lab changes what is expected from you as you progress.

PHASE 01 · EXPT 1–2

👀 Understand

Robot hardware, Linux, ROS 2 computation graph, command-to-motion, sensor visualisation and safety.

PHASE 02 · EXPT 3–6

⌨️ Build

Write nodes, interface sensors, implement kinematics and odometry, create reactive control and depth-triggered behaviour.

PHASE 03 · EXPT 7–10

🧪 Investigate

The problem is given. The method is not. You design experiments, collect evidence, analyse errors and engineer solutions.

PHASE 04 · EXPT 11

🚀 Create

Build an application using SLAM + Nav2, validate it experimentally and defend your engineering decisions.

The rule changes halfway through.

Early: “Here is the method. Make it work.”   →   Later: “Here is the problem. Figure out how to prove your solution works.”

03 · YOUR EXPERIMENT MAP

11 missions.
One autonomous robot.

Each experiment adds a new capability. By the end, the pieces connect into a complete autonomy stack.

EXPT 01 · DEMO · 4 H01

Meet the Robot + Linux

Identify the mechanical, electrical, sensing and computing subsystems. Trace software → controller → motors → motion → measurement. Get independent with Linux and SSH.

YOU LEARN: robot architecture · Linux · SSH · safety · signal paths
EXPT 02 · DEMO · 4 H02

ROS 2: From Command to Motion

Create a workspace, package and node. Understand nodes, topics and messages. Teleoperate the robot, inspect /cmd_vel and /odom, visualise sensors in RViz2 and record a reference bag.

YOU LEARN: ROS 2 graph · colcon · launch · RViz2 · TF2 · rosbag
EXPT 03 · EXERCISE · 4 H03

Multi-Sensor ROS 2 Interfacing

Build Python nodes subscribing to LiDAR, IMU and odometry. Extract meaningful quantities, handle invalid data and diagnose silent communication failures caused by QoS, remapping, domain or driver issues.

YOU LEARN: Python nodes · callbacks · QoS · diagnostics · launch files
EXPT 04 · EXERCISE · 4 H04

Differential-Drive Kinematics + Odometry

Derive wheel-to-body motion, implement discrete odometry, publish pose/transform and compare commanded, reported and physically measured trajectories.

YOU LEARN: kinematics · dead reckoning · odometry · error · wheel slip
EXPT 05 · EXERCISE · 4 H05

LiDAR Obstacle Detection + Reactive Navigation

Turn LaserScan data into sector-wise free-space information. Build emergency stop, turn-to-free-space and proportional wall-aware behaviours, then test them against challenging obstacles.

YOU LEARN: LaserScan · control loops · parameters · stopping distance · failure modes
EXPT 06 · EXERCISE · 4 H06

RGB-D Depth Perception

Process depth images, reject invalid pixels, extract robust obstacle distance and trigger a controlled stop for obstacles outside the LiDAR scan plane. Characterise depth accuracy and surface failures.

YOU LEARN: depth images · ROI · calibration · 3D perception · camera limits
EXPT 07 · ENQUIRY · 4 H07

How Wrong Is Odometry?

The robot says it travelled two metres. Did it? Design straight, square and circular campaigns across distances, surfaces and rotation directions. Fit a quantitative error model.

YOU LEARN: hypothesis · replication · drift · systematic/random error · model fitting
EXPT 08 · ENQUIRY · 4 H08

LiDAR vs RGB-D: Who Should You Trust?

Compare ranging performance across distance, object size, surface, incidence angle, illumination and height. Report bias, dispersion, RMSE, relative error and availability.

YOU LEARN: sensor physics · test matrices · statistics · sensor selection
EXPT 09 · ENQUIRY · 4 H09

Sensor Fusion + Localisation

Compare encoder-only, IMU-only and fused pose estimates. Sweep fusion parameters, configure the transform tree and evaluate an extended Kalman filter against an independent reference.

YOU LEARN: fusion · EKF · frames · bias/noise · localisation
EXPT 10 · ENQUIRY · 6 H10

Design Your Own Local Navigator

Move six metres through an obstacle field without contact. You choose the architecture, sensor arbitration, thresholds, control law, state machine, recovery and independent safety limiter.

YOU LEARN: navigation design · safety · recovery · parameter justification · robustness
EXPT 11 · OPEN-ENDED · ESA · 6 HFINAL

Build an Autonomous Mobile Robot Application

Teams of three select an application-oriented problem. Build an occupancy-grid map using SLAM, evaluate it, deploy and tune Nav2, integrate perception + estimation + planning + control, benchmark against a baseline and defend the result.

YOU LEARN: SLAM · mapping · localisation · costmaps · planners · controllers · recovery · experimental validation

05 · THIS IS HOW YOU'LL BE ASSESSED

Your marks reward engineering.

The assessment structure follows the same progression as the learning journey.

10Demonstrations · Expt 1–2
20Exercises · Expt 3–6
40Structured enquiry · Expt 7–10
20Open-ended project · Expt 11 / ESA

What gets noticed?

  • Can you plan and execute independently?
  • Does your implementation work beyond the exact demo?
  • Did you measure and repeat rather than guess?
  • Can you diagnose a fault systematically?
  • Can your conclusion be defended from your own data?

The “very good” mindset

  • Define success before collecting data.
  • Use adequate replication and report dispersion.
  • Trace parameters back to measurements.
  • Handle variations, boundary conditions and induced faults.
  • State limitations honestly — strong engineering includes knowing what your experiment does not prove.
